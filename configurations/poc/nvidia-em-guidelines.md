# NVIDIA EM guidelines

| # | Rule and why | Example and usage |
|---|---|---|
| 1 | **Topology file.** **Rule:** The platform topology says what exists on the platform and how it is wired and reached. Devices and their instances are described only there. Each fact (EID, port, GPIO, parent, bridge) is written once and referenced everywhere else with a variable.<br>**Why:** One place answers what is on the platform, and a fact written twice cannot drift apart. | `HGX_GPU_1` in `vrnvl-hmc-ast2700-platform-topology.json` states its kind, instance, parent, `"EID": 12`, bridge `HGX_GPU_SMA_0` and `"PoolIndex": 1`. The entity files only read `$EID` and `$PoolIndex`. |
| 2 | **Policy file.** **Rule:** The policy file holds the behaviour choices a platform makes: a limit, an interval, a reaction, an exclusion. A platform that needs a device or generation to behave differently says so here and never edits the entity file.<br>**Why:** The entity file is shared by every platform. A policy entry stays with the platform that chose it. | The BF4 firmware-update exclusion is a `PLDMExclusion` entry in `vrnvl-platform-policy.json`, not a line in the shared bluefield file. A platform that enables fewer GPU capabilities would list its own `Disable` set in its policy. † |
| 3 | **Entity file.** **Rule:** An entity file carries only what differs between generations of a device kind. `Generation` names the product generation (`vera-rubin`), never a platform, SoC or board.<br>**Why:** The file is shared by every platform that uses the device, so it must say nothing that is true of only one of them. | In `vr-rot.json` the IRoT block states `Disable: [Device.ChassisIRoTResponder]` and nothing the default already does. Every probe in the POC uses `'Generation': 'vera-rubin'`, not `vr-bmc`, `vr-hmc` or `AST2700`. |
| 4 | **Board file.** **Rule:** A board file holds the inventory and wiring of its FRU-found board and does not repeat entity content. EM owns inventory only for FRU boards. A device found over a protocol gets its inventory from its daemon.<br>**Why:** Every object has one owner and every fact one copy. | `boards/HPM_HMC_PG558.json` holds the board, its location and the CPLD record. The CPU's daemon exposes are in `vera-cpu.json`. An nsmd-managed GPU has no EM inventory record, because nsmd creates it. † |
| 5 | **Backend code.** **Rule:** A default that is the same for every generation of a device, such as an enabled feature, belongs in the backend daemon code, not in EM config.<br>**Why:** Writing it in config copies code into every platform, and the copies drift when the code changes. † | The nsmd default model switches every GPU feature on. `rubin-gpu.json` lists only `Disable` and `ParameterOverrides`, instead of the roughly 30 `NSM_*` records it replaced. |
| 6 | **Reuse.** **Rule:** A new platform writes a topology, and a policy only where it deviates. It reuses the existing entity and board files, copies nothing and puts no platform name in a shared file.<br>**Why:** This is the port-effort goal: the new platform adds only what is new. | The AST2600 and AST2700 BMCs share `vr-bmc-cx9_io.json`, `vr-bmc-cx_sma.json` and the boards. Only the two topology files differ. Where both SoCs must agree (CX9 `poweredInStandby`), one value is chosen and written in the shared file. |
| 7 | **New entity.** **Rule:** When a new device kind is introduced, its base capabilities are written in the backend code first, as the default (base) profile of that kind and generation. The entity file is created afterwards and carries only the deviation from that base profile, so a device that matches the base has an empty entity record.<br>**Why:** Capabilities written in the entity file are copied into every platform and drift from the code. The base profile is the one place a capability is defined, and the entity file stays small and reviewable. † | `vera-cpu.json` and `vr-bmc-hpm_sma.json` have an `NSM_Telemetry` item with `"Disable": []` and `"ParameterOverrides": {}`: the device matches the base profile in the code. `rubin-gpu.json` lists only six `Disable` entries and a few overrides, the deviation of this GPU from its base. Adding a new device means the nsmd owner adds its base profile first, and the entity file starts empty. |
| 8 | **Associations.** **Rule:** For the objects a backend daemon creates, the daemon manages every association inside one entity, using standard D-Bus object paths derived from the device kind, instance and prefix. It does not rely on association paths written in EM config. An association that connects two different entities (a device to its parent, bridge or board) is created by the daemon from the topology information only.<br>**Why:** The paths are derivable, so a path written in config is a copy that breaks when a name changes. The topology already states which entity connects to which, so it is the only config input the daemon needs. † | Today a GPU's `NSM_Temp` item carries `Associations` entries with full paths to its chassis and its processor. With the rule, nsmd derives those from the standard paths (`chassis/HGX_GPU_N`, `accelerator/HGX_GPU_N`) and the entry is dropped. The link from `HGX_GPU_0` to its processor module comes from `"ParentChassis": "HGX_ProcessorModule_0"` in the topology. |

† Depends on daemon or EM code that is not written or not yet run on a device.
